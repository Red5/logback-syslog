Chapter 5: Message formats

The appender can send the traditional BSD format (RFC 3164, the default) or the structured format of RFC 5424. Both carry a priority, which is computed from the facility and the event's level.

Severities and facilities

The priority is facility × 8 + severity. Logback levels map to syslog severities like this:

Logback levelSyslog severity
ERROR3 (err)
WARN4 (warning)
INFO6 (info)
DEBUG, TRACE7 (debug)

Facility names and their numbers are the standard ones (USER is 1, LOCAL0 is 16, and so on up to LOCAL7 at 23).

RFC 3164 (default)

The frame is <PRI>TIMESTAMP HOST TAG: MESSAGE. The timestamp and host name are included unless you set sendLocalTimestamp or sendLocalName to false, and appName supplies the tag. For protocol UNIX the host name is omitted by default (sendLocalName defaults to false there), giving <PRI>TIMESTAMP TAG: MESSAGE as glibc's syslog() writes to the local socket.

<134>Oct  1 09:17:11 red5host red5: [main] org.red5.server.Demo stream started

RFC 5424

Set <rfc5424>true</rfc5424>. The frame is <PRI>1 TIMESTAMP HOST APP-NAME PROCID MSGID STRUCTURED-DATA MESSAGE:

  • The timestamp is ISO 8601 with an offset and at most six fractional digits.
  • APP-NAME is appName (- if unset). PROCID and MSGID are always -.
  • STRUCTURED-DATA is built from the structuredData elements, or is - when none are configured.
  • The timestamp and host name are always sent, so sendLocalName and sendLocalTimestamp do not apply.

With this configuration:

<appender name="SYSLOG" class="org.red5.logback.syslog.SyslogAppender">
  <syslogHost>127.0.0.1</syslogHost>
  <port>514</port>
  <facility>LOCAL0</facility>
  <rfc5424>true</rfc5424>
  <appName>red5</appName>
  <suffixPattern>%logger %msg</suffixPattern>
  <structuredData>
    <id>meta@32473</id>
    <entry><name>app</name><value>live</value></entry>
  </structuredData>
</appender>

the message from Chapter 2 becomes:

<134>1 2026-10-01T09:17:22.726761-07:00 red5host red5 - - [meta@32473 app="live"] org.red5.server.Demo stream started

Stack traces and multi-line text

Syslog messages are single lines, so the appender never sends a line break inside a message:

  • The text produced by suffixPattern is split at line breaks into separate syslog messages (blank lines are skipped).
  • Exceptions are rendered with stackTracePattern and sent after the log message, one syslog message per line. For example %ex{short} sends only the first lines, and %rEx prints the root cause first.
  • Throwable converters in suffixPattern (%ex, %xEx, %rEx and the like) print nothing, so a stack trace is never sent twice.
  • Set throwableExcluded to true to send only the log message.

Every line of one event repeats the same priority, header and (in RFC 5424) structured data. This is what the two-line exception in Chapter 2 looks like in RFC 5424 mode:

<131>1 2026-10-01T09:17:22.729268-07:00 red5host red5 - - [meta@32473 app="live"] org.red5.server.Demo publish failed
<131>1 2026-10-01T09:17:22.729888-07:00 red5host red5 - - [meta@32473 app="live"] java.lang.IllegalStateException: no codec
<131>1 2026-10-01T09:17:22.730017-07:00 red5host red5 - - [meta@32473 app="live"] 	at org.red5.server.Demo.main(Demo.java:12)

Message length

maxMessageLength is the size in bytes of one syslog message including its header, between 128 and the transport's limit. The default is 1024 for RFC 3164 and 2048 for RFC 5424. What happens to a longer message depends on the format:

ModeBehaviour
RFC 3164The message is split into several syslog messages, each marked at the join with ....
RFC 5424The message is truncated to fit (RFC 5424 section 6.1), at a UTF-8 character boundary. Splitting would repeat the header fields in the middle of a message, so it is not done.

For UDP and for unix datagram sockets (UNIX with unixSocketType DATAGRAM) the limit cannot exceed 65507 bytes, the largest UDP datagram; a larger value is lowered with a warning, so an oversized datagram can never block the backlog. Receivers often have limits of their own, commonly 1024 to 8192 bytes, so a value above what your collector accepts only moves the truncation to the other side.

Replayed messages

A message that was backlogged while the server was unreachable is replayed with the replay time in its header. If the exact event time matters, add %d to suffixPattern (for example %d{ISO8601} %logger %msg) so the original time is part of the message text.
