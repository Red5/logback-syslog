Chapter 6: Reliability

Logging must never make the application slower or fail. The appender is designed around that: logging calls hand the event to a queue and return, a single background thread does the network work, and anything that cannot be delivered is either kept in a bounded backlog or counted as dropped. This chapter describes what happens at each step and which status messages tell you about it.

The asynchronous queue

By default (sync is false) the logging call formats nothing and does no I/O: it captures the event (thread name, MDC and so on) and puts it on a bounded queue of queueSize events. One daemon thread named red5-syslog-<appender name> takes events off the queue in order, formats them, and sends them.

When the queue is full

  • blockWhenFull=false (default): the new event is discarded and counted. The logging call returns immediately. The first discard, and then at most one more every 10 seconds, produces a warning in Logback's status output: syslog queue full; N events dropped so far.
  • blockWhenFull=true: the logging call waits until there is room. This loses nothing, but a slow or unreachable server will then slow the application down. Use it only when completeness matters more than latency.

A queue that fills up usually means the server (or the network path to it) cannot keep up. Raising queueSize buys time but not throughput; each queued event holds its message in memory.

When the server cannot be reached

With TCP, TLS or unix sockets, a failed connect or write moves the message to the backlog: a ring buffer of backlogSize formatted messages (default 1000). The appender then reports the problem once (an error in the status output, at most one every 10 seconds, for example syslog destination unavailable: ConnectException: Connection refused).

It keeps trying to reconnect, but not on every event: after a failure it waits 1 second, then 2, 4, 8, and so on up to 30 seconds between attempts, and starts again from 1 second after a success. While it waits, messages go straight into the backlog. If the backlog is full, the oldest message is evicted and counted as dropped.

When the server answers again, the backlog is replayed in order, before any newer message, and the appender records syslog destination recovered; replayed N backlogged messages. Replayed messages carry the time of the replay in their syslog header; see Chapter 5 for adding the original time to the text.

Set backlogSize to 0 to disable the backlog. Failed messages are then counted as dropped immediately.

UDP

UDP has no connection and no delivery feedback, so a stopped server cannot be detected: the datagrams are simply lost, and nothing is backlogged or counted. Use TCP or TLS when messages must not be lost. A UDP send that fails locally (for example, network unreachable) is backlogged and replayed like any other failure.

The dropped counter

Every event that is not delivered is accounted for: delivered, still waiting in the backlog, or counted in getDroppedCount(). The counter includes events discarded when the queue was full, backlog messages that were evicted, messages that could not be written with no backlog, and anything still queued or in the backlog when the appender stopped. One event that produces several syslog messages (a stack trace, for example) counts as one while it is queued and as its individual messages once it is in the backlog.

Shutdown

When Logback stops the appender (at context shutdown, or when a web application is undeployed), it:

  • stops accepting events,
  • waits up to shutdownTimeoutMs (default 2 seconds) for the writer to send what is queued, with 0 meaning do not wait,
  • if the writer is still blocked on the network after that, aborts the connection so that the thread ends, and
  • counts whatever is left, then records one warning with the total: syslog appender [SYSLOG] stopped; N events dropped in total (M while stopping); K messages were still in the backlog. Nothing is logged if the total is zero.

Stopping an appender twice, logging after it has stopped, and starting it again on the same context are all safe. The backlog does not survive a stop: it is in memory only.

Synchronous mode

sync=true sends on the calling thread, with no queue. Delivery is simpler to reason about, but every logging call waits for the network, and with TCP or TLS a stalled server stalls the application. Replay of a backlog then happens on the next logging call. Prefer the default.
