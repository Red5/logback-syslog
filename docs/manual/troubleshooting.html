Chapter 8: Troubleshooting and limitations

The appender does not start

The appender validates its settings when it starts. If one is invalid it records an error and stays inactive; no events are sent and nothing is thrown into your application. Look for a line of this form in the status output (enable debug="true"):

ERROR in org.red5.logback.syslog.SyslogAppender[SYSLOG] - syslog appender [SYSLOG] not started: port out of range 1..65535: 0

The checks are: a non-empty suffixPattern (and stackTracePattern unless throwableExcluded); a positive queueSize; a non-negative shutdownTimeoutMs and backlogSize; a maxMessageLength of at least 128; a non-empty host and a port from 1 to 65535 (for UNIX: a non-empty unixSocketPath, a non-null unixSocketType, and for DATAGRAM that unix datagram sockets are available); for TLS, a trust store or key store; and for rfc5424 a valid appName and valid structuredData (ids and names 1 to 32 printable ASCII characters without space, =, ] or "; ids unique).

For TLS the trust store and key store files are loaded at start, so a wrong path or password shows up here too, as not started: File does not exist … or a keystore error.

A misspelled property name or an unknown modifier class is reported by Logback itself, as an error about a missing setter or class, and the appender starts without it.

Messages are missing

  • UDP: a datagram to a stopped or unreachable server is lost silently. Switch to TCP to detect and recover from outages.
  • The logger level. The appender receives only what Logback's logger levels let through. Check the root and logger levels.
  • Queue full. Look for syslog queue full warnings and read getDroppedCount() (Chapter 6).
  • The receiver truncates or drops long lines. Many collectors limit message size. Lower maxMessageLength to what yours accepts.
  • The program name or facility is not what the server filters on. Check facility and appName; rsyslog and syslog-ng route on both.
  • The timestamp is in the wrong time zone. RFC 3164 timestamps carry no time zone: the receiver interprets them. RFC 5424 timestamps include the offset.

TLS problems

Status message containsCause
No subject alternative DNS name matching … foundThe certificate does not list syslogHost. Use a name that is in the certificate, or reissue it.
PKIX path building failedThe trust store does not contain the server's issuer. Import the certificate chain, or use a trust store that has it.
Remote host terminated the handshake, or a timeoutThe port does not speak TLS (a plain TCP port was used), or the server requires a client certificate (set sslKeyStore).

Unix socket does not work

The status output names the cause, with the system error:

Message containsCause and fix
unix datagram sockets are unavailableThe appender did not start: the platform (for example Windows) or the JVM does not allow datagram sockets. Use unixSocketType STREAM, or UDP or TCP to 127.0.0.1.
ENOENTNothing exists at unixSocketPath: the daemon is not running or uses another path (/var/run/syslog on macOS).
ECONNREFUSEDThe path exists but nobody is reading it: a stale socket file, or not a socket at all.
EPROTOTYPEThe daemon listens on a stream socket. Set unixSocketType to STREAM.
EACCESThe application's user may not write to the socket.
EAGAIN or ENOBUFSThe daemon's receive buffer is full; messages wait in the backlog and are replayed.

If messages arrive but journalctl -t does not find them under your appName, check that sendLocalName is not set to true: a host name in the header is read as the tag. See Chapter 4.

Frequently asked questions

Does the appender block my application when the syslog server is down?

Not with the default settings: events go to a queue and a background thread handles the network. With blockWhenFull=true or sync=true it can.

Can I use several appenders?

Yes: for example one UDP appender for a local daemon and one TLS appender for a remote service, each with its own name, queue and backlog. They share nothing.

Is the order of messages preserved?

Yes, per appender: events are sent in the order they were logged, and a replayed backlog goes out before newer messages. UDP itself does not guarantee ordering on the network.

Which Logback and Java versions are supported?

Java 21 or later, Logback 1.5.x and SLF4J 2.x.

Can I add the time of the event to a replayed message?

Yes: include %d in suffixPattern. See Chapter 5.

Known limitations

  • Unix datagram sockets need native access through java.lang.foreign (a preview API in Java 21, used reflectively, so no flag is needed). The JDK prints a one-time warning unless the JVM runs with --enable-native-access=ALL-UNNAMED. They work on Linux and macOS only (macOS untested); Windows is unsupported.
  • TCP framing is LF-delimited. Octet-counted framing (RFC 6587) is not implemented, so a receiver that accepts only octet-counted frames cannot read the stream.
  • TLS needs a trust or key store configured. To use the Java default trust (public authorities), point sslTrustStore at cacerts.
  • Stopping a TLS appender against a peer that has stopped reading can take about 2.5 seconds longer than shutdownTimeoutMs, because closing a TLS socket waits briefly for the blocked write.
  • Replayed messages carry the replay time in their syslog header (see Chapter 5).
  • The backlog is in memory and is lost when the application stops.
  • The host name is resolved once. A UDP target whose address changes needs an appender restart.
  • Only the prefix, suffix and HTML-escape modifiers can be configured in XML.
