Chapter 1: Introduction

Syslog is the standard way for Unix-like systems, network devices and log services to collect log messages. Logback ships a SyslogAppender, but it speaks only UDP, always uses the older RFC 3164 format, and sends from the thread that logs. This project provides an appender with the same basic properties and adds the transports, formats and delivery guarantees that production servers tend to need.

What you get

  • Transports: UDP, TCP, TLS (with host name verification) and unix domain sockets. See Chapter 4.
  • Formats: RFC 3164 and RFC 5424, including structured data, plus a set of message modifiers. See Chapter 5.
  • Delivery behaviour you can rely on: logging calls do not block, events that cannot be sent are kept in a bounded backlog and replayed in order, reconnects back off, and every lost event is counted. See Chapter 6.
  • One jar: the syslog4j client, message layer and server are included, repackaged under org.red5.syslog. The only dependencies are Logback and SLF4J, which Red5 already provides. See Chapter 7.

Requirements

ComponentVersion
Java21 or later
Logback1.5.x (logback-classic)
SLF4J2.x (slf4j-api)

Logback and SLF4J are declared with provided scope: the jar does not bundle them.

Relationship to other projects

Logback's SyslogAppender. The core appender properties use the same names as ch.qos.logback.classic.net.SyslogAppender: syslogHost, port, facility, suffixPattern, stackTracePattern and throwableExcluded.

The papertrail appender. com.papertrailapp.logback.Syslog4jAppender (papertrail/logback-syslog4j) wraps syslog4j in a Logback appender. This project offers the same capability, with the syslog4j classes included in the jar, but it is configured with flat properties rather than a nested syslogConfig element. The mapping is shown below.

syslog4j. The library is a port of syslog4j 0.9.46. Nothing is lost except the log4j integration. The package names and a few details differ; they are listed in Chapter 7.

Migrating

From Logback's SyslogAppender

Change the class name. The existing properties keep their meaning.

logback.xml
<appender name="SYSLOG" class="org.red5.logback.syslog.SyslogAppender">
  <syslogHost>logs.example.com</syslogHost>
  <port>514</port>
  <facility>LOCAL0</facility>
  <suffixPattern>[%thread] %logger %msg</suffixPattern>
</appender>

From the papertrail Syslog4jAppender

The papertrail appender takes a nested layout and syslogConfig. Translate them to flat properties as follows.

papertrailRed5 Logback Syslog
syslogConfig class=…SSLTCPNetSyslogConfig<protocol>TLS</protocol>
syslogConfig class=…TCPNetSyslogConfig<protocol>TCP</protocol>
syslogConfig class=…UDPNetSyslogConfig<protocol>UDP</protocol> (the default)
<host><syslogHost>
<port><port>
<ident><appName>
<maxMessageLength><maxMessageLength> (UDP is capped at 65507 bytes, see Chapter 5)
<layout>…<pattern><suffixPattern> for the message, <stackTracePattern> for exceptions
logback.xml
<appender name="SYSLOG" class="org.red5.logback.syslog.SyslogAppender">
  <syslogHost>logs.example.com</syslogHost>
  <port>6514</port>
  <protocol>TLS</protocol>
  <appName>my-app</appName>
  <maxMessageLength>128000</maxMessageLength>
  <sslTrustStore>/etc/red5/syslog-truststore.p12</sslTrustStore>
  <sslTrustStorePassword>changeit</sslTrustStorePassword>
  <suffixPattern>%-5level %logger{35}: %m</suffixPattern>
</appender>
Layout pattern differences

The papertrail example uses %-5level %logger{35}: %m%n%xEx. Here suffixPattern is the text of one syslog message, so leave out %n and the exception converters: the appender splits multi-line text into separate syslog messages itself and sends exceptions separately through stackTracePattern. See Stack traces.
